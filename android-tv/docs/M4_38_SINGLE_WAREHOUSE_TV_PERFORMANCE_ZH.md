# HERRIN M4.38 — 单仓性能回归与遥控器跟手优化

## 目标与边界

用户反馈 TCL T7L Ultra 的 HERRIN 明显没有网易爆米花、Netflix 顺滑，希望用已有单仓发现问题后自行修复。

本轮基于 M4.37 Draft PR #44（`ff55a5baf751494763ac47c6c6146c9db925aed7`）建立独立 Draft PR；不修改原 PR/main，不降低媒体播放质量、不通过延长 spinner 掩盖卡顿。

### 可确认的现有性能风险
1. `MainActivity` 在浏览页面组合与任意遥控焦点动画发生时重新计算 `showCatalog.search` / `collapse`，逐条读取观看历史并排序；同一海报的观看进度也会重复访问本地历史。
2. TMDB 对每个结果单独更新 `providerFilms`；最多 240 条数据可能多次重新计算整个海报墙与历史展示，造成卡顿和焦点微跳。
3. 上下推荐海报行切换此前使用最长 1.1 秒的 `animateScrollToItem`，焦点必须等待动画滚动后才能命中目标。
4. 分类/屏幕切换触发约 260ms 的整页渐入，即使数据和目标已经准备好，也会人为延长视觉响应。

### 已实现的优化
- 对首页筛选/检索、历史驱动排序及每张卡片的观看进度使用依赖精确的 Compose `remember`，避免遥控器一帧一帧重复计算或访问 SharedPreferences。播放页退出重新进入列表时恢复读取最新历史。
- `catalogIdentity` 缓存于目录列表变化时，不再每次焦点重组都遍历全部标题。
- TMDB 网络仍最多三路并发，但每 **12** 个结果批量提交一次目录 UI 状态，而不是每处理一部就全列表 `map`、重建海报。刮削结果保留原片源、线路、选集与人工纠错逻辑；同步更新进度。
- 上下海报行切换改为直接定位 `scrollToItem`，没有最长 1.1 秒等待；初次启动保留简短品牌入场动画，后续切分类不再做整页额外 260ms 渐入。
- 不关闭焦点状态反馈、不减少真实内容、不绕过 Play/Spider 授权。
- **已验证单仓冷启动优先本地缓存**：如果用户此前已成功导入且校验通过，重启时直接从已验证的本地 JSON 恢复站点列表，不再等待远端单仓 8 秒连接/读取超时；后台只更新磁盘缓存供下次启动使用，不在用户操作途中强制刷新主页。用户在设置里主动“应用/刷新”仍直接请求网络，保持手动获取最新配置。新增真实 HTTP + 缓存测试验证首次不发请求、手动更新发请求、HTTP 许可不能被缓存绕过。


## 第二轮：卡片图片解码与 GPU 负载优化

真实代码检查发现 `FilmArtwork.kt` 每次 LazyRow 卡片复用时都可能重新执行文件读取、位图解码；卡片宽度仅约 217dp，历史默认位图仍可被解码到 **1200×1600**，每张海报还要绘制额外的模糊副本。

已经落实以下改动：
- 新增进程级、随设备内存上限动态调整的 **8–32MB 解码后 Bitmap LRU**，通过缓存文件路径、图像尺寸角色（hero/card）、修改时间及文件大小校验，防止图片已清理或已损坏时继续使用旧内存内容。
- 同 URL 图片加载使用固定 64 条细粒度锁条带防止重复下载；网络至多 4 路并发，避免海报墙第一次加载时发起过多图片请求。
- 普通卡片采用最大约 **640×960** 的解码限制与 `RGB_565`，不降低全屏背景图的 `ARGB_8888` 质量。
- 去掉每张卡片焦点变化时全屏小卡的 `blur(10–12dp)` GPU 模糊副本，改为暗色源图背景及前景清晰展示；**全屏电影背景保留原有视觉效果**。
- 将焦点按钮文字色和描边的原 190ms 颜色补间改为首帧立即切换，只对位置变化保留短动画；对按键与海报焦点日志使用惰性 Lambda，普通用户未开启 Debug 时不构造高频字符串。
- 新增 Android instrumentation 检查同一图片被复用时返回**同一内存 Bitmap 对象**、磁盘缓存损坏会使内存缓存失效并重下、超大海报卡片被降采样、Hero 图片仍有足够分辨率。
- 竖版海报快速移动时，全屏 Hero 背景图片网络加载延迟 110ms 后才启动，避免每个一闪而过的焦点都立即下载/解码最高 2560px 大图；卡片淡入从 280ms 收敛为 120ms，让图片更快达到全不透明。

此阶段需要重新检查 Android Debug、Lint、JVM 和电视模拟器全部测试，尤其要确保损坏缓存回退、TV 画质和扫码/弹幕无回归。不能把第一轮的 98/98 自动套用为第二轮结果。

## 单仓压力测试

新增 Android TV instrumentation `M438SingleWarehousePerformanceTest`：
- 使用 `MockWebServer` 返回单个 TVBox 仓库 JSON，含 **12 个站点**（1 个可授权 CMS、11 个不执行的 Spider 占位站），然后返回 **60 部电影**（当前 CMS 解析器单页上限）。
- 验证导入配置时只访问 **1 次仓库 JSON**，不执行 11 个第三方 Spider/JAR，不在导入阶段加载 CMS 列表。
- 用户选择影视点后才实际加载 60 部电影和海报墙，服务器总请求应为 2。
- 使用真实 Android TV 的 `sendKeyDownUpSync` 注入 **16 次连续 DPAD_RIGHT**。测量从系统按键派发到 Compose idle 的 P50/P95；`FrameMetrics.TOTAL_DURATION` 记录电视窗口合成帧 P95 和超过 16ms 的样本数。
- 作为保守回归保护，对遥控器 P95 设置 **1500ms 严重停顿上限**；它不是“Netflix 级别已达标”的判断。P95 和合成帧数据都会以脱敏 `HerrinPerf` 事件写到 `HERRIN-emulator-evidence/performance-measurements.log`。
- 测试仅针对无版权的合成片名、空海报与本地授权测试服务器，不加载第三方视频、账号/Token、JAR 或不透明解析插件。

## 关于真实单仓、真机与 Netflix 对比

- 用户提供的饭太硬地址 `http://www.饭太硬.net/tv` 在此环境无法可靠获取响应；公开聚合项目 2026-10-30 的自动监测也有该域名获取失败记录。因此这轮不能谎称“已经在同一个远端站点完成端到端实播和测速”。
- 用户已在 TCL 测试过单仓的真实影片和 Spider 交互；那属于**实机兼容与网络延迟**，本次 Android 模拟器的数据仅是稳定可重复的 UI 基准。
- 要严格与网易爆米花、Netflix 对标，仍需同一 TCL 电视采集三个 App 的相同操作：冷启动/温启动、方向键到焦点反应 P95、打开详情、点击到首帧、滑动及 60 秒掉帧。不同应用可能走不同内容源和解码器，不应把公网加载延迟等价于 Compose 渲染掉帧。
- 下一轮可增加连接真实单仓时的**仅元数据阶段**逐请求时长与 HTTP 状态采集，不自动执行任何不明 JAR 或追踪私人授权。真人使用下，质量目标建议 DPAD 交互 P95 不超过 100–150ms、低长帧率、转场能即时响应；这些是后续真机目标，不是本次取得的测量结果。

## 首轮实际性能基线（已取得，2026-10-30）

来自 GitHub Actions [Android TV 模拟器 run 40989034110](https://github.com/shawnhhh/aura-tv/actions/runs/40989034110) 的 `HERRIN-emulator-evidence/performance-measurements.log`，对应 PR #45 提交 `7addfd7368933c4dda6967511c4a30247868d036`：

| 单仓指标 | 实际测量 |
| --- | ---: |
| 导入仓库配置（MockWebServer 本地） | **190ms** |
| 选择 CMS 后加载 60 部电影 | **199ms** |
| 16 次遥控器右键 P50 | **164ms** |
| 16 次遥控器右键 P95 | **199ms** |
| 采样合成帧 P95 | **150ms** |
| 超过 16ms 的样本数 | **39/39** |

说明：这项按键耗时包含 Android 实际遥控输入注入、Compose 空闲等候及可能的焦点视觉动画，**不是单纯 native focus 事件至首个画面的延迟**。模拟器软件渲染所测 `FrameMetrics` 不能直接推断 TCL 的物理面板 FPS；但它能够作为每个构建在相同运行环境下的相对参考。

第一轮优化通过 **98/98** 项 Android TV 模拟器测试，Debug 编译/JVM/Lint 也通过。接下来将焦点文字和描边立即切换，缩短海报位置动画并提升焦点动画的 spring 响应；第二轮以新 CI 的测量进行同环境比较，防止单纯凭感觉宣称性能提升。遥控器严重停顿的 CI 守门值从 1500ms 收紧到 **600ms**，仍与最终目标 100–150ms 明确区分。
