# HERRIN M4.46：可取消的海报缓存互斥锁

## 为什么还要修一层

M4.44 把网络下载名额分成 3 张普通海报 + 1 张当前 Hero，并在下载前/中加入协程取消检查。但是 `AuthorizedPosterCache` 为避免重复下载，同一份 URL 会被一个固定条带锁保护。原来只有 **64 条 Java `synchronized` 锁**，整个图片缓存查询、磁盘文件读取、网络下载和解码都包在锁内。

在 60 张海报的首页冷加载阶段，不同 URL 的哈希可能落在同一条带。这不影响正确性，却可能让一张已经被 D-pad 快速略过的图片仍在等待别人的网络请求；普通 Java `synchronized` 的阻塞等待无法主动检查 Compose 协程是否已经取消。增加网络 permit 的取消检查并不能解决**卡在条带锁前**的任务。

## 本轮开发内容

1. 新增 `PosterStripeGate`（128 个公平性不承诺的 `ReentrantLock`），减少不同 URL 哈希发生偶然条带碰撞的机会，不增加网络最大并发。
2. 条带锁获取改为每 35ms `tryLock`，从调用方传入 `Job.isActive` 状态。焦点离开造成请求取消时，即使另一张图片一直占用锁，该等候任务也能退出。
3. 拿到锁后再次确认任务有效；如果恰好在获锁时取消，主动 unlock，避免泄露锁。所有磁盘/网络/内存路径通过 `try/finally` 在原线程释放锁；保留同 URL 串行缓存和去重逻辑。
4. 新增四组 JUnit：
   - 不同条带互不等待；
   - 旧请求正在等待同条带时取消可退出；
   - 获取锁之后取消，不泄漏；
   - 同 URL 的请求不会并行下载，旧请求释放后新请求才能继续。
5. Android TV 真实图像、网络许可、海报裁切、缓存文件限制、播放器和 D-pad 测试全部照常执行。

## 不能夸大的地方

- 每 35ms 检查取消只作用于**排队等锁**的阶段。已经进入网络 `InputStream.read` 的工作仍受到本地网络读取超时限制；没有承诺瞬时杀掉线程。
- 128 条带降低哈希碰撞机会，但不是保证完全无碰撞。只有同一 URL 必须串行，偶然碰撞也需保持正确锁语义。
- 网络测试和 JVM 测试证明正确性，真正的 TCL 电视帧流畅度仍需真机采样才能与 Infuse/VidHub 对比。
- 以 M4.45 的相同模拟器图形基线和 M4.43 焦点 P95 衡量持续改进，不把一次 CI 的 CPU 抖动当作用户体验回归。
